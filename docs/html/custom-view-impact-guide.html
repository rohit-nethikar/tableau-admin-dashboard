01 · Mental model

How a Custom View actually persists

A Custom View is not stored inside the workbook file. It's a server-side snapshot — saved filters, sorts, parameter overrides, zoom, and selection state — layered on top of one specific base View. Two identifiers hold that layering together, and nearly every way a workbook change breaks a view is really just one of these two moving out from under it.

View identity

Resolved by sheet or dashboard name inside the workbook's LUID. Rename the sheet and the server can no longer connect the saved snapshot to it — a rename looks identical to a delete-and-recreate.

Field identity

Native fields are keyed by database column name. Calculated fields get an internal token assigned once, at creation — e.g. [Calculation_1428251562548719617] — that survives a caption rename. Delete and recreate the calc, and it's a new token wearing an old name.

02 · Tier 1

Breaks outright

Changes that orphan or corrupt saved state

Each of these severs one of the two identifiers above. The saved view either stops loading, silently resets the piece of state that referenced it, or — in the last row — is destroyed independent of any content change at all.

Auto-detectedcaught by Workbook Compare today Best-effortflagged, but with a known blind spot — see the note Manual checkno structural diff can see this — verify by hand
Sheet or dashboard renamed or deleted Auto-detected
View lookup is by name inside the workbook's LUID — a rename reads as delete-plus-new. Every custom view built on it orphans.
A calc deleted and recreated with the same caption Auto-detected
The internal token is reassigned. Every stored filter, sort, or pill referencing the old [Calculation_…] token now dangles — invisibly, because the caption looks unchanged. Surfaces as a "field removed" finding; the tool doesn't yet call out the recreation explicitly.
Field removed entirely Auto-detected
Stored filters or sorts referencing its internal name can no longer resolve.
Field datatype changed on a field used in a stored filter Auto-detected
Saved values — a string vs. a number, a date range — can become invalid on reload.
Parameter removed Auto-detected
Any saved override for it resets to nothing.
Filter card removed, or its field removed Auto-detected
The saved member or range selection for that filter is dropped.
Live data-source connection changed (server, database, credentials), or a live connection disappears entirely Auto-detected
Custom views may silently show different data, or fail to load if the new connection is unreachable.
Row-level security (data-source) filter added, removed, or its condition changed Auto-detected
Gates what rows a saved custom view can even see — treated as High regardless of direction, since there's no "cosmetic" version of an RLS change.
Mark type changed (e.g. Bar to Line) Auto-detected
Selected marks and formatting tied to the old mark type in a saved custom view can resolve differently or disappear entirely.
A Group or Set removed Auto-detected
Saved filters or sorts referencing it will reset or fail to resolve.
A worksheet's tab hidden (removed from Show Sheets as Tabs) Best-effort
Breaks custom views tied to it, even if it's later unhidden. Only evaluated when both the published and candidate workbook actually carry window-state info; a workbook with no <windows> section at all is left unknown rather than assumed hidden.
Workbook republished as a new object, not overwritten in place Manual check
A Save-As, or a migration path that doesn't preserve the workbook LUID, orphans every custom view for it — regardless of whether a single pixel of content changed. This is the single most common way admins lose custom views during a real migration. The workbook's LUID isn't part of the .twb XML, so no structural diff — this tool included — can see a Save-As coming.

03 · Tier 2

Degrades silently

Changes that shift behavior without an error

Nothing here throws an error or an obviously broken view. The risk is a saved view that loads fine but no longer means what the user thinks it means. Same detection key as Tier 1 above.

Field role changed (dimension ↔ measure) Auto-detected
Shelf placement, sort, and legend state built on the old role may not survive reload.
Filter condition narrowed or widened on an unchanged field Auto-detected
Default members or range bounds shift; a saved selection may no longer match and can silently reset to the new default.
New filter added to an existing sheet Auto-detected
A custom view's underlying data may not satisfy the new filter's default condition — it can render with no data and no error.
A calculation rewritten to reference different fields Auto-detected
Downstream filters or sorts built on that calc may behave differently even though the calc "still exists" by name.
Shelf or encoding pills changed (rows, columns, color, size, label) Auto-detected
A saved view may not restore its exact pill layout.
Table-calc addressing changed (Compute Using / partitioning) without touching the formula Manual check
Running totals, rank, and percent-of-total silently recompute differently. The formula text never moved, so a text-only diff misses it entirely — this app doesn't parse table-calc addressing yet.
Group bucket membership edited Auto-detected
A saved filter still names the group — what's inside the group changed underneath it.
Set definition or computed condition changed Best-effort
Same failure mode as groups: a set used on a shelf or in a filter silently changes membership. Value-list Sets share Groups' XML shape and are caught the same reliable way; a computed/condition Set is matched by calculation class and hasn't been verified against a real-world export, so treat a clean result here with some caution.
"Only Relevant Values" dependency changed Manual check
If the parent filter's field or values change, a dependent filter's saved selection can silently reset. This dependency link isn't parsed yet.
Filter, highlight, or parameter action retargeted or removed Best-effort
Doesn't corrupt already-saved state, but breaks the interaction a user relied on to reach that state. Removal and a change in action type (e.g. filter action swapped for a highlight action) are both caught; a same-type retarget — still a filter action, but now pointing at a different field or sheet — isn't distinguished yet.
Data-source join, relationship, or custom SQL changed Manual check
Can shift the query grain silently — worksheets don't error, the numbers just move. Join/relationship/custom-SQL structure isn't parsed yet.
Parameter caption renamed Auto-detected
A caption rename alone doesn't invalidate a saved selection — the internal identity is unchanged — but is called out separately from a type/value/domain change, which can.
Parameter's allowable-values domain or range narrowed Auto-detected
A saved parameter selection that falls outside the new range or member list may invalidate on reload.
Quick-filter card hidden ("Show Filter" turned off) while the filter condition stays applied Auto-detected
Distinct from the filter card being deleted outright — the condition still applies, but users lose the ability to change the saved selection interactively.

04 · Tier 3

Cosmetic, safe

Changes that don't touch saved state

Internal identifiers are untouched, so the saved view carries over exactly as the user left it. Workbook Compare still surfaces these as informational, Low-severity findings — verified by the test suite to never rank as impacting — since something built on them today may depend on them tomorrow.

  • Caption or display-name rename — the internal token underneath is unchanged.
  • Number formatting, default aggregation, or a field's description/comment.
  • Sort order that ends up matching what was already saved.
  • A brand-new sheet or dashboard that nothing else references yet.
  • A new parameter, Group/Set, or dashboard action added — nothing references it yet.
  • A quick-filter card newly shown, or a previously-hidden worksheet's tab becoming visible again.

05 · Outside the file

Migration risk a workbook diff can't see

These don't show up in any structural comparison of the .twb — the file can be byte-for-byte the same and the view can still land wrong.

Row-level security tied to Group names Manual check

A filter using USERNAME() or ISMEMBEROF('Region: West') doesn't error on a new site — it just returns whatever that condition resolves to there. If the destination site has no Group of that exact name, the same custom view quietly shows different, often empty, data.

Project moves and permission inheritance Manual check

Custom views typically inherit permissions from the workbook rather than carrying their own. Moving a workbook to a new project can change who can even open a saved view, independent of anything inside it.

Publish mechanics, restated Manual check

Worth repeating outside Tier 1: overwrite preserves the workbook's LUID and everything hanging off it. Delete-and-republish, or a migration tool that creates a new content object, does not — this is a process risk, not a content risk, and it dwarfs everything else on this page when it goes wrong.

06 · Before you publish

Pre-migration checklist

  1. Publish via Overwrite, or a LUID-preserving migration path — never delete-and-republish an existing workbook.
  2. Diff the .twb structurally before and after. A visual side-by-side can't see internal field tokens, so it can't catch a delete-and-recreate hiding behind an unchanged caption.
  3. Confirm every field used in a stored filter still exists and kept its datatype.
  4. Re-check any calculation that was deleted and recreated during the edit, even when the caption is identical to before.
  5. If the destination is a different site, confirm every Group referenced by ISMEMBEROF() or USERNAME() exists there under the same name.
  6. Spot-check one custom view per affected sheet after publishing. A diff tool tells you what changed — not that a human confirmed the view still looks right.
